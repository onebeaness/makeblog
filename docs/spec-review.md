# MVP 명세(REV 0.1) 비판적 검토

원본 명세를 그대로 구현하면 **동작하지 않는다.** 기능이 부족해서가 아니라,
명세가 스스로 세운 완료 기준과 충돌하는 구조를 지시하기 때문이다.
아래는 구현하면서 실제로 부딪힌 순서대로 정리한 것이다.

각 항목의 등급:
**[치명]** 그대로 하면 안 돌아감 · **[오류]** 사실이 틀림 · **[빈틈]** 빠져 있음 · **[의견]** 판단 차이

---

## A. 구조

### A1. [치명] 세션이 어디에 사는지 명세에 없다

명세는 "Server Component 우선"(02절)과 "Supabase Auth"(02절)만 말하고,
**세션 토큰을 어디에 저장할지**를 말하지 않는다. 이게 이 명세의 가장 큰 구멍이다.

`supabase-js` 의 기본 저장소는 브라우저 `localStorage` 다. 그러면:

```
브라우저: 로그인됨 (localStorage 에 토큰 있음)
서버:     로그인 안 됨 (아무것도 못 봄) → auth.uid() = NULL
```

서버에서 `auth.uid()` 가 NULL 이면 `with check (auth.uid() = user_id)` 도,
`using (auth.uid() = user_id)` 도 전부 거짓이 된다.
**명세가 설계한 RLS 정책 3개 중 2개가 서버에서 항상 실패한다.**

해결은 세션을 **쿠키**에 두는 것이다. 쿠키는 매 요청마다 서버로 가기 때문이다.
`@supabase/ssr` 의 `createServerClient` 가 그 일을 한다.
여기에 만료된 토큰을 갱신할 proxy(구 middleware)가 하나 더 필요하다.

→ 구현: `src/lib/supabase/server.ts`, `src/lib/supabase/session.ts`, `src/proxy.ts`

### A2. [치명] 04절이 06절·07절과 모순된다

04절은 `/write` 를 **Client Component** 로 지정한다.
그런데 거기서 `supabase.from("posts").insert()` 를 부르면,
그 요청은 **브라우저에서 나간다.** Network 탭에 그대로 보인다.

07절 완료 기준은 이렇게 적혀 있다:

> Server Component 상태에서 Network 탭에 수파베이스 요청이 **보이지 않는다**

둘 다 만족할 수 없다. 그리고 06절은 클라이언트 직접 호출이 **왜 위험한지**를
가르치는 절이다. 정상 경로를 그 위험한 모양으로 만들어 놓고
"이건 위험하다"고 가르치는 셈이다.

원인은 04절의 전제에 있다. 명세는 이렇게 쓴다:

> `/write` 와 `/auth` 만 Client Component 인 이유는 입력값을 실시간으로 다뤄야 하기 때문이다

**입력값을 다루는 것과 데이터베이스를 호출하는 것은 다른 일이다.**
폼 상태(타이핑, 검증, 버튼 비활성화)는 Client 가, DB 호출은 Server Action 이 한다.
App Router 에서는 이게 기본형이다.

→ 구현: `src/app/write/write-form.tsx`(Client, 폼 상태만) +
`src/app/actions/posts.ts`(`"use server"`, DB 호출)

### A3. [치명] 작성자 이름을 표시할 방법이 없다

04절 와이어프레임에는 이렇게 적혀 있다:

```
RLS를 처음 만났을 때
2026-08-21 · 원빈
```

그런데 03절의 데이터 모델에는 작성자 이름을 담을 열이 없고, 테이블은
`posts` 하나뿐이다. `auth.users` 는 anon key 로 조회할 수 없다 —
수파베이스가 그 스키마에 권한을 주지 않기 때문이다.

**이름을 넣으려면 셋 중 하나를 골라야 한다:**

| 방법 | 대가 |
| --- | --- |
| `posts.author_email` 에 복사 | 06절의 "숨겨야 할 값과 공개할 값을 같은 테이블에 두지 말라"와 정면 충돌 — 이메일이 모든 방문자에게 나간다 |
| `profiles` 테이블 추가 | "테이블 1개" 약속이 깨진다. 대신 1:1 관계와 트리거를 배운다 |
| 작성자 이름을 빼기 | 화면이 초라해진다 |

이 구현은 **세 번째**를 골랐다. "테이블 1개 · 정책 3개"라는 명세의 약속을
지키는 쪽이 MVP 답기 때문이다. 대신 자기 글에는 "내 글" 표시를 붙였다.

v2 에서 이름이 필요하면 `profiles` 가 정답이다:

```sql
create table public.profiles (
  id uuid primary key references auth.users(id) on delete cascade,
  display_name text not null check (char_length(display_name) between 1 and 40)
);
alter table public.profiles enable row level security;
create policy "profiles_select_public" on public.profiles for select to anon, authenticated using (true);
create policy "profiles_upsert_own"    on public.profiles for insert to authenticated with check (auth.uid() = id);
create policy "profiles_update_own"    on public.profiles for update to authenticated
  using (auth.uid() = id) with check (auth.uid() = id);
```

여기서 핵심은 **이메일이 아니라 표시 이름을 공개한다**는 점이다.
명세 06절의 교훈을 그대로 적용한 결과다.

## B. 사실관계

### B1. [오류] "삭제로 Update 계열 RLS는 이미 체험됨"

01절에서 글 수정을 제외하는 근거다. 틀렸다.

| 작업 | 필요한 절 |
| --- | --- |
| DELETE | `using` 만 |
| UPDATE | `using` **과** `with check` **둘 다** |

`using` 은 "어떤 행을 건드릴 수 있나", `with check` 는 "바꾼 결과가 규칙에 맞나"를 본다.
UPDATE 는 둘 다 필요하다 — 내 글을 남의 글로 바꿔치기하는 것을 막아야 하니까.

명세는 07절에서 스스로 이렇게 인정한다:

> **글 수정** — `using` 과 `with check` 를 동시에 쓰는 유일한 작업

같은 문서 안에서 앞뒤가 다르다. **제외하는 결정 자체는 옳다.** 근거만 틀렸다.
정확한 근거는 "MVP 가 증명하려는 한 줄과 무관하다"이다 — 명세가 다른 항목에서
쓴 바로 그 기준이다.

### B2. [오류] "남의 글 삭제가 실패하는지 직접 확인" (05절 5단계)

**실패하지 않는다. 조용히 0행이 지워진다.**

`using` 조건에 맞지 않는 행은 애초에 그 사용자에게 *보이지 않는다.*
그래서 `delete from posts where id = '남의글'` 은 에러가 아니라
"조건에 맞는 행이 없음" = 정상 종료 = 0행이 된다.

로컬 PostgreSQL 로 확인한 결과다:

```
PASS  A 가 B 의 글을 지우면 0건 (에러 아님) (= 0)
PASS  A 가 자기 글을 지우면 1건 (= 1)
```

이걸 모르면 **아무것도 지우지 않고 "삭제되었습니다"라고 말하는 UI** 가 나온다.
데이터는 안전하지만 사용자에게 거짓말을 하는 화면이다.

→ 구현: `deletePost` 가 `.select()` 를 붙여 영향 행 수를 세고, 0이면
"삭제할 권한이 없습니다"를 돌려준다. (`src/app/actions/posts.ts`)

### B3. [오류] "RLS 는 행 단위이지 열 단위가 아니다" (06절)

결론은 맞지만 서술이 과하다. PostgreSQL 에는 **열 단위 권한**이 있다:

```sql
revoke select on public.posts from anon;
grant  select (id, title, created_at) on public.posts to anon;
```

이러면 anon 은 `content` 나 `user_id` 를 아예 조회할 수 없다.

"숨겨야 할 값과 공개할 값을 같은 테이블에 두면 안 된다"는 여전히 좋은 조언이다.
열 권한은 관리가 번거롭고, `select *` 가 에러를 내는 등 함정이 있기 때문이다.
다만 "불가능하다"가 아니라 "권하지 않는다"가 정확하다.

### B4. [오류] "서버 전용 비밀 키가 없다 → API Route 없이 Server Component 만으로 완성된다" (02절)

인과가 틀렸다. Server Component 만으로 되는지는 **키의 문제가 아니라 두 가지에 달려 있다.**

1. 세션을 쿠키로 서버까지 나르는가 (→ A1)
2. 쓰기 경로를 어디에 두는가

서버 전용 키가 없어도 **쓰기에는 Server Action(또는 Route Handler)이 필요하다.**
Server Component 는 렌더링만 하고 폼 제출을 받지 못한다.

명세가 하려던 말 — "이 프로젝트에는 숨겨야 할 키가 없으므로 구조가 단순하다" — 은
맞다. 다만 그 결론이 "API 계층이 아예 없다"까지 가면 안 된다.

### B5. [빈틈] RLS 를 켜라는 말이 없다

03절은 "RLS 정책 3개"를 표로 보여준다. 그런데 이 한 줄이 없다:

```sql
alter table public.posts enable row level security;
```

**RLS 가 꺼져 있으면 정책은 전부 장식이다.** 정책을 만들어도 아무것도 검사하지 않는다.
수파베이스 대시보드에서 테이블을 만들면 기본으로 켜지지만, SQL 로 만들면 꺼진 채로
생긴다. 명세는 SQL 로 만드는 흐름인데 이 줄이 빠져 있다.

초보자가 가장 자주, 가장 조용하게 넘어가는 지점이다.
"정책을 다 만들었는데 왜 아무나 지워지지?" 가 여기서 나온다.

→ 구현: `0001_posts.sql` 에 `enable` 과 `force` 를 둘 다 넣고 주석을 달았다.

### B6. [빈틈] GRANT 라는 층이 통째로 빠져 있다

명세는 "실제 방어선은 오직 RLS 정책뿐이다"(06절)를 반복한다.
정확히는 **두 층**이다.

| 층 | 단위 | 질문 |
| --- | --- | --- |
| `GRANT` | 테이블 · 열 | 이 롤이 이 작업을 **시도라도** 할 수 있나 |
| RLS | 행 | 그 중 **어떤 행**에 대해 허용되나 |

`grant` 가 없으면 RLS 를 볼 것도 없이 거부된다.
수파베이스가 신규 테이블에 기본 권한을 자동으로 줘서 안 보일 뿐이다.

이게 왜 중요하냐면 — 이 프로젝트에서 UPDATE 를 막는 방법이 두 가지이기 때문이다.
"UPDATE 정책을 안 만든다"(RLS 층)와 "UPDATE 권한을 안 준다"(GRANT 층).
둘을 같이 하면 정책 실수로 구멍이 생겨도 권한이 막는다.

→ 구현: `0001_posts.sql` 이 필요한 권한만 명시적으로 준다. UPDATE 권한은 주지 않는다.

## C. 완료 기준의 검증력

### C1. [의견] "Network 탭에 수파베이스 요청이 보이지 않는다"는 약한 기준

이건 "우리 앱이 서버에서 읽는다"를 확인할 뿐, **데이터가 안전한지**는 확인하지 않는다.
공격자는 우리 앱을 쓰지 않는다.

더 강한 기준은 이것이다 — **앱을 거치지 않고 직접 때려보기:**

```bash
# 로그아웃 상태로 남의 명의 글을 밀어넣어 본다
curl -s -X POST "$SUPABASE_URL/rest/v1/posts" \
  -H "apikey: $ANON_KEY" \
  -H "Content-Type: application/json" \
  -d '{"title":"침입","content":"","user_id":"<아무 uuid>"}'
# → 401 / "new row violates row-level security policy" 가 나와야 한다
```

이게 통과해야 06절의 결론("실제 방어선은 RLS")이 증명된다.
Network 탭을 보는 것은 그 앞의 준비 운동이다.

### C2. [빈틈] "다른 사용자의 글은 삭제되지 않는다"를 확인할 준비가 없다

명세 어디에도 **두 번째 계정을 만들라**는 말이 없다. 시드 데이터도 사용자 하나를
가정한다. 사용자가 하나면 이 기준은 검증 자체가 불가능하다.

그리고 B2 때문에, "삭제 버튼을 눌렀는데 아무 일도 안 일어남"과
"삭제가 성공함"을 화면에서 구분할 수 없다.

### C3. [빈틈] 완료 기준이 전부 수동이다

RLS 는 SQL 로 자동 검증할 수 있다. 수파베이스도, 네트워크도 필요 없이
로컬 PostgreSQL 만으로 된다.

→ 구현: `supabase/tests/` 에 13개 항목을 넣었다. `./supabase/tests/run.sh` 로 돈다.
`auth.users` · `auth.uid()` · `anon`/`authenticated` 롤을 흉내 낸 shim 위에
**실제 마이그레이션 파일을 그대로** 올려서 검사하므로, 정책을 고치면 테스트가 잡는다.

## D. 데이터 모델

03절의 표는 열 이름과 한 줄 설명만 있다. 실제로 SQL 을 쓰려면 다음이 더 필요하다.

| 빠진 것 | 왜 필요한가 |
| --- | --- |
| `check (char_length(btrim(title)) between 1 and 200)` | "빈 문자열 금지"가 말로만 있다. 공백만 넣으면 통과한다 |
| `user_id default auth.uid()` | 클라이언트가 `user_id` 를 아예 안 보내게 된다. 남의 id 를 보낼 기회 자체가 사라진다 |
| `content` 길이 상한 | anon key 로 누구나 INSERT 할 수 있다. 상한이 없으면 한 번에 DB 를 채울 수 있다 |
| `on delete cascade` | 사용자가 탈퇴하면 글이 고아가 된다 |
| `created_at desc` 인덱스 | 목록은 항상 이 순서로 읽는다 |
| `enable row level security` | → B5 |

### [빈틈] 속도 제한이 없다

로그인만 하면 무제한으로 글을 쓸 수 있다. RLS 는 **"누가"** 를 막지
**"얼마나"** 를 막지 않는다. MVP 범위 밖인 건 동의하지만,
"anon key 를 공개해도 된다"의 대가가 무엇인지는 명세 어딘가에 한 줄 있어야 한다.
수파베이스 대시보드의 Auth rate limit 과, 필요하면 `posts` 에
"최근 1분 내 N개 이하" 같은 정책을 거는 방법이 있다.

## E. 디자인과 접근성

### E1. [오류] 팔레트의 대비가 기준에 못 미친다

04절이 지정한 무채색 6단계 중, 메타 정보에 쓰라고 한 `#8C8C8C` 는
흰 배경에서 **대비 3.0:1** 이다. WCAG AA 의 본문 텍스트 기준은 4.5:1 이다.

색을 빼는 디자인일수록 이게 치명적이다. **대비가 유일한 위계 수단이기 때문이다.**
색이 있으면 "파란 링크"로 구분되지만, 무채색에서는 명도 차이밖에 없다.
그런데 그 명도 차이를 읽을 수 없는 사람이 있다면 위계가 통째로 사라진다.

→ 구현: 위계를 유지한 채 한 단계씩 조였다.

| 용도 | 명세 | 이 구현 | 대비 |
| --- | --- | --- | --- |
| 제목 | `#101010` | `#101010` | 21.0:1 |
| 본문 | `#565656` | `#4A4A4A` | 8.9:1 |
| 메타 | `#8C8C8C` | `#6B6B6B` | 3.0:1 → **5.3:1** |

### E2. [의견] "빨강 대신 확인 절차" — 좋은 선택이다

색으로 위험을 표현할 수 없을 때 **절차로 대신한다**는 판단은 옳다.
색맹 사용자에게는 원래 빨강도 신뢰할 수 없는 신호이므로,
이 제약이 오히려 더 나은 패턴을 강제했다.

다만 무채색에서는 **초점 표시(focus ring)** 도 같은 문제를 겪는다.
키보드 사용자가 지금 어디 있는지 모르게 된다.
→ 구현: `:focus-visible` 에 `--ink` 색 2px outline 을 명시했다.

### E3. [빈틈] 다크 모드 언급이 없다

명세 문서 **자신은** 다크 모드를 지원한다(`prefers-color-scheme` 블록이 있다).
그런데 블로그 팔레트는 라이트 6색만 준다. 무채색 디자인에서 다크 모드는
"색을 뒤집으면 되는" 일이 아니다 — 명도 위계를 다시 짜야 한다.

→ 구현: `globals.css` 에 라이트/다크 두 벌의 토큰을 정의했다.

## F. 운영과 보안

### F1. [빈틈] "Confirm Email 을 끄라"는 경고가 너무 가볍다

02절은 준비 단계에서 이걸 끄라고 한다. 실습 편의로는 맞다.
그런데 되돌리라는 말은 07절 v2 목록의 **한 줄**로만 있다:

> **배포** — 로컬 밖에서 접속. 이때 Confirm Email 을 다시 켠다

끈 채로 배포하면 **존재하지 않는 이메일로 계정이 무한히 만들어진다.**
경고는 끄라고 말하는 그 자리에 있어야 한다.

### F2. [빈틈] 로그인 실패 메시지가 정보를 흘린다

"등록되지 않은 이메일입니다" 와 "비밀번호가 틀렸습니다" 를 구분해 주면,
**어떤 이메일이 가입되어 있는지** 알려주는 셈이다.
→ 구현: 둘 다 "이메일 또는 비밀번호가 올바르지 않습니다"로 합쳤다.

### F3. [빈틈] `/write` 에 비로그인 상태로 들어가면?

04절 표에 `/write` 의 "대응 정책"은 `INSERT` 로만 적혀 있다.
접근 자체를 어떻게 다룰지는 없다. 폼을 보여주고 제출할 때 실패시킬 것인가,
아예 못 들어오게 할 것인가.

→ 구현: proxy 가 `/auth?next=/write` 로 보내고, 페이지에서도 한 번 더 확인한다.
proxy 는 편의(빠른 리다이렉트)이고 **진짜 차단은 서버와 RLS** 라는 것을
주석으로 남겼다.

### F4. [의견] "마크다운 제외"가 곧 안전은 아니다

지금은 본문이 plain text 이고 React 가 자동으로 이스케이프하므로 안전하다.
그런데 v2 에서 마크다운을 넣는 순간 **`dangerouslySetInnerHTML` 을 쓰게 되고,
그 순간 XSS 가 열린다.** 명세의 v2 목록에 "마크다운 → sanitize 필요"가
한 줄 있어야 한다. RLS 는 이걸 막지 못한다 — 저장된 값 자체는 합법이니까.

## G. 잘 되어 있는 것

비판만 늘어놓으면 공정하지 않다. 이 명세가 특히 잘한 것들:

- **제외 근거를 "어렵다"가 아니라 "무관하다"로 썼다.**
  MVP 범위를 정하는 가장 좋은 기준이다. (B1 의 자기모순만 빼면)

- **4단계에서 RLS 오류를 일부러 만나게 한다.**
  `new row violates row-level security policy` 를 한 번 직접 보는 것과
  설명으로 읽는 것은 다르다. 학습 설계로 훌륭하다.

- **06절의 결론이 정확하다.** "UI 에 버튼이 없다는 것은 막혀 있다는 뜻이 아니다."
  이 한 문장이 이 챕터 전체의 값어치다.

- **색을 빼서 타이포 위계를 강제한 것.** 제약이 판단을 대신하게 만드는 좋은 예다.

- **단계마다 커밋, 실험 전 백업.** 되돌릴 수 있는 상태를 유지하라는 지시가
  구현 순서에 박혀 있다.

## H. 명세를 이렇게 고치면 된다

REV 0.2 를 쓴다면 최소한 이 다섯 가지:

1. **02절에 "세션은 쿠키에 둔다 (`@supabase/ssr`)" 를 추가.** 그리고
   "서버 전용 키가 없으니 API 계층이 없다"를 "쓰기는 Server Action 이 받는다"로 교체.
2. **04절 렌더링 열을 `Client(폼) + Server Action(호출)` 로 정정.**
   와이어프레임의 작성자 이름은 빼거나 `profiles` 를 범위에 넣는다.
3. **03절에 `enable row level security` 와 `default auth.uid()`,
   `check` 제약을 명시.** 표가 아니라 실제 SQL 로.
4. **01절의 글 수정 제외 근거를 "MVP 의 한 줄과 무관하다"로 교체.**
   05절 5단계의 "삭제가 실패하는지"를 "0행이 지워지는지"로 정정.
5. **07절 완료 기준에 `curl` 직접 호출 테스트를 추가.**
   두 번째 계정 만들기를 구현 순서 5단계에 명시.

그리고 04절 팔레트의 `#8C8C8C` 를 `#6B6B6B` 로.
색을 뺀 디자인에서 대비는 취향이 아니라 기능이다.
