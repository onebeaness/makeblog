## ① 데이터에 주소가 있다

> 확인된 지점: 메서드와 URL의 조합까지는 읽힘. **JSON을 직접 해독한 경험이 없어 감에 의존**하고 있었음.

### JSON은 부품이 네 개뿐이다

```
"문자열"              따옴표가 있으면 글자
123 / true / null    따옴표가 없으면 숫자·참거짓·비어있음
{ }                  객체 — 이름표가 붙은 묶음. 사물 하나.
[ ]                  배열 — 순서가 있는 나열. 여러 개.
```

나머지는 전부 이 넷을 겹쳐 놓은 것.

### 읽는 규칙 한 줄

> **`{` 를 보면 "사물 하나", `[` 를 보면 "목록".**

API 응답의 대부분은 이 형태다.

```json
[ { ... }, { ... }, { ... } ]
```
→ **"사물들의 목록"**. 게시글 목록, 사용자 목록, 댓글 목록이 전부 이 모양.

### 핵심 독법: 보낸 것과 받은 것을 나란히 놓는다

**요청 본문** (책 175쪽)
```json
{ "title": "첫 번째 글", "content": "안녕하세요, 블로그를 시작합니다." }
```

**응답 본문** (책 176쪽)
```json
{
  "id": "abc123",
  "title": "첫 번째 글",
  "content": "안녕하세요, 블로그를 시작합니다.",
  "authorId": "user456",
  "createdAt": "2024-01-15T09:30:00Z"
}
```

늘어난 세 개가 **서버가 결정한 것**이다.

| 늘어난 것 | 누가 정했나 |
|---|---|
| `id` | 서버(DB)가 부여 |
| `authorId` | 서버가 **토큰을 보고** 채움 |
| `createdAt` | 서버가 시각을 찍음 |

**이 차이가 "클라이언트가 주는 것"과 "서버가 결정하는 것"의 경계선이다.**
`authorId`를 클라이언트가 보내게 두면, 그 값을 남의 id로 바꿔 보내는 순간 남의 이름으로 글이 써진다.

그래서 이 정책이 존재한다.
```sql
with check (auth.uid() = user_id)
```
"네가 보낸 `user_id`가, 네 토큰에서 꺼낸 진짜 신원과 같을 때만 통과."
요청 JSON과 서버가 아는 사실을 대조하는 장치다.

> **어떤 API를 보든 이 diff를 먼저 한다.**
> 요청에만 있는 것 / 응답에만 새로 생긴 것 → 그 시스템에서 누가 무엇을 통제하는지 그대로 드러난다.

#### diff란

두 개를 나란히 놓고 **달라진 부분만** 뽑아내는 것. `git diff`, "이 PR의 diff" 할 때의 그 단어.
여기서는 **요청 JSON의 이름표 목록 vs 응답 JSON의 이름표 목록**을 비교하라는 뜻.

절차: ① 요청 이름표 적기 → ② 응답 이름표 적기 → ③ 세 칸에 나눠 담기

| 어디에 있나 | 의미 |
|---|---|
| 양쪽 다 | 클라이언트가 정했고 서버가 받아들인 것 → **위조 가능성을 의심할 것** |
| 응답에만 | 서버가 만들어낸 것 → **클라이언트가 손댈 수 없는 것** |
| 요청에만 | 서버가 받아 쓰고 돌려주지 않은 것 |

로그인 예시에서 세 번째 칸의 의미가 분명해진다.

```
요청  { "email": "...", "password": "1234abcd" }
응답  { "user": {...}, "access_token": "eyJhbGci..." }
```
- `password` → 요청에만. 확인용으로 받아 쓰고 안 돌려줬다. **이게 정상.**
  응답에 `password`가 들어 있으면 그 자리에서 사고다.
- `access_token` → 응답에만. 서버가 발급한 신분증(JWT).
  이후 모든 요청의 `Authorization` 헤더에 실려 간다.

`authorId`가 응답에만 있는 것도 같은 이유다.
요청에도 있었다면 "남의 id를 적어 보낼 수 있다"는 뜻이 된다.

### Network 탭 URL 해독 (책 209쪽)

```
posts?select=id%2Ctitle%2Ccontent&order=created_at.desc
```
`%2C` = 쉼표(URL 표기). 풀면:
```
posts?select=id,title,content&order=created_at.desc
```
- `posts` → posts 테이블에서
- `select=id,title,content` → 이 세 열만
- `order=created_at.desc` → 최신순

SQL로는 이것과 같다.
```sql
select id, title, content from posts order by created_at desc;
```

**브라우저 주소창에 SQL이 거의 그대로 드러나 있다.** 수파베이스가 테이블을
이런 URL 형태의 API로 자동 노출하기 때문(= 대시보드의 PostgREST).
그래서 클라이언트 직결이 편리한 동시에, RLS가 없으면 위험하다.
이 URL은 누구든 복사해서 직접 칠 수 있다.

### 실무 팁

개발자 도구에서 **Response 탭 말고 Preview 탭**을 본다.
Response는 한 줄로 뭉쳐진 원문이고, Preview는 접었다 폈다 할 수 있게 정리해준다.
(책 210쪽 스크린샷의 `▶ 0`, `▶ 1`, `▶ 2` = 배열 안의 객체 세 개)

읽는 순서:
1. 바깥이 `{`인지 `[`인지 확인
2. `[`면 몇 개인지 세기
3. 첫 번째 하나만 펴서 이름표 목록 확인
4. 나머지는 같은 모양이니 건너뛰기

## ② 상태는 화면 밖에 산다

> 확인된 지점: 3. 호출과 캐시는 스스로 짚음.
> **막힌 곳 = 에러 코드로 탐지하는 습관이 통하지 않는 구간.**

### 전제: 상태 코드는 서버가 자의로 붙인다

규격이 강제하지 않는다. 실패인데 `200 OK`로 내리고 본문에 `{"success": false}`를
담는 API가 흔하다. 상태 코드만 보면 성공처럼 보인다.

### 함정 ① RLS는 에러를 내지 않는다

조회가 RLS에 막히면 `401`도 `403`도 아니다.
```
200 OK
[]
```
**성공했고 결과가 0건.** "글이 없는 블로그"와 "볼 권한이 없는 블로그"의
응답 형식이 완전히 같다. 에러 코드 기반 탐지가 여기서 무너진다.

### 함정 ② 캐시는 요청 자체를 안 보낸다

Network 탭에 그 요청이 **아예 없다.** 실패한 요청을 찾으면 안 나온다.
**없다는 것이 증상이다.**

### 진실의 사본이 여러 벌 있다

```
DB (원본)
  ↓  쿼리 + RLS 필터        ← 조용히 0건이 될 수 있음
서버가 만든 응답
  ↓  Next.js 캐시            ← 옛날 것이 그대로 나갈 수 있음
브라우저가 받은 것
  ↓  렌더링 / 필터
화면
```

"DB엔 있는데 화면엔 없다"의 3대 원인 = **호출 / 캐시 / 권한**

### 좁혀 들어가는 순서

| 순서 | 확인 방법 | 결론 |
|---|---|---|
| 1. DB에 진짜 있나 | Table Editor에서 눈으로 | **없다** → 쓰기 문제. 여기서 끝 |
| 2. 요청이 나갔나 | Network 탭 | **요청이 아예 없다** → **캐시** |
| 3. 응답이 비었나 | Preview 탭에서 `[]` 확인 | **`200`인데 `[]`** → **RLS 또는 쿼리 조건** |
| 4. 응답엔 있는데 화면엔 없나 | 응답과 화면 대조 | 렌더링·필터·정렬 |

**2번에서 요청이 없으면 3·4번은 볼 필요가 없다.**

### 책 207쪽 버그의 실제 원인

> "생성 성공 메시지가 나오고 DB에 데이터가 정상 생성돼. 그러나 홈페이지에는 안 보여."

1번 통과(DB에 있음) → 2번에서 걸린다.
Next.js는 서버 컴포넌트 페이지를 캐시해두고 재사용한다.
DB에 새 글이 들어가도 **홈페이지는 물어보지 않는다. 요청이 안 나간다.**

해결책은 캐시를 다시 만들라고 알려주는 것:
`revalidatePath`, `router.refresh()`, `revalidate` 설정.

책은 이 원인을 밝히지 않고 "AI에게 상황을 설명해 고쳐달라"로 넘어간다.
고쳐지긴 하지만 왜 그랬는지가 안 남는다.
