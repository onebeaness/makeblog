# 파트 A. 사전 지식 (173~180쪽)

앞 챕터에서 화면만 만들었다면, 이번엔 **데이터를 저장하고 불러오는** 단계.
외부 컴포넌트(수파베이스)를 붙이기 위한 최소 지식.

## A-1. REST API란? (173~176쪽)

### A-1-1. 클라이언트-서버 통신의 기본 구조 (173쪽)
- 클라이언트 = 사용자가 보고 상호작용하는 부분 (브라우저, 모바일 앱)
- 서버 = 데이터 저장 + 비즈니스 로직 처리 + 요청에 응답
- "새 글을 저장해줘" → 서버가 DB에 저장 → "저장 완료" 응답
- **이 요청/응답이 REST API의 핵심**

### A-1-2. HTTP 메서드 (173~174쪽)
- HTTP = 브라우저와 서버가 데이터를 주고받는 통신 규칙
- 규칙이 있어서 `GET`이라고 하면 "데이터 달라는 뜻이구나" 하고 알아들음
- HTTPS = HTTP에 보안 강화, 기본 구조는 동일
- 핵심 4개 메서드

  | 메서드 | 의미 | 예시 |
  |---|---|---|
  | GET | 데이터 조회 | 글 목록 불러오기 |
  | POST | 새 데이터 생성 | 새 글 작성하기 |
  | PUT | 기존 데이터 수정 | 글 내용 업데이트 |
  | DELETE | 데이터 삭제 | 글 삭제하기 |

- 이 4개 = **CRUD** (Create / Read / Update / Delete)
- 블로그의 모든 기능은 결국 이 4가지의 조합
- HTTP는 **무상태(stateless)** — 각 요청은 독립적으로 처리됨

### A-1-3. 엔드포인트 설계 (174~175쪽)
- 엔드포인트 = 어떤 자원에 접근할지 나타내는 URL
- `/posts`, `/posts/123`, `/posts/123/comments`
- 메서드 + 엔드포인트 조합으로 의도가 드러남
  - `GET /posts` 글 목록 조회
  - `GET /posts/123` 123번 상세 조회
  - `POST /posts` 새 글 생성
  - `PUT /posts/123` 123번 수정
  - `DELETE /posts/123` 123번 삭제

### A-1-4. 요청과 응답 뜯어보기 (175~176쪽)
- **요청(Request)** 구성 요소
  - 시작 줄: HTTP 메서드 + 엔드포인트 (`POST /api/posts HTTP/1.1`)
  - 헤더(Headers): 요청의 부가 정보 (`Host`)
  - `Content-Type`: 보내는 데이터의 형식 (JSON)
  - `Authorization`: 인증 토큰 — 로그인한 사용자임을 증명 (`Bearer ey...`)
  - 본문(Body): 실제 전송 데이터 (JSON)
- **응답(Response)** 구성 요소
  - 상태 줄 (`HTTP/1.1 201 Created`)
  - `Content-Type`
  - 본문: 생성된 리소스 (`id`, `title`, `content`, `authorId`, `createdAt`)

### A-1-5. HTTP 상태 코드 (176쪽)

| 코드 | 의미 | 설명 |
|---|---|---|
| 200 | OK | 조회·수정 등 요청 성공 |
| 201 | Created | 새 자원 생성 성공 |
| 400 | Bad Request | 입력값 오류 등 잘못된 요청 |
| 401 | Unauthorized | 로그인 등 인증 필요 |
| 403 | Forbidden | 권한 없음 (남의 글 수정 시도) |
| 404 | Not Found | 자원을 찾을 수 없음 |
| 500 | Internal Server Error | 서버 내부 오류 |

- 프런트엔드는 상태 코드를 보고 사용자에게 적절한 메시지를 보여줌
  (401 → 로그인 페이지 이동, 404 → "글을 찾을 수 없습니다")

> **체크포인트 A-1**
> 1. `POST /posts`와 `GET /posts/123`이 각각 무슨 뜻인지 설명해봐.
> 2. 401과 403의 차이를 블로그 상황으로 각각 예를 들어봐.
> 3. Authorization 헤더가 없으면 서버는 몇 번 코드를 돌려줄까?

## A-2. SQL 데이터베이스란? (176~178쪽)

관계형 DB = 데이터를 **테이블 형태**로 저장. 엑셀 스프레드시트를 떠올리면 됨.

### A-2-1. 테이블 구조 (177쪽)
- 행(Row): 하나의 데이터 레코드 = 게시글 하나
- 열(Column): 데이터의 속성 = `title`, `content`, `author_id`
- 기본키(Primary Key): 각 행을 고유하게 식별하는 열, 보통 `id`

### A-2-2. 테이블 관계 (177~178쪽)
- 외래키(Foreign Key) = 다른 테이블의 기본키를 참조하는 열
  - `posts.author_id` → `users.id`
- "첫 번째 글의 작성자는 김개발"이라는 연결이 **DB 수준에서 보장**됨
- 제약(Constraint)으로 강제 → **데이터 무결성** 보장
- 애플리케이션 수준에서도 관리 가능하지만, DB에서 강제하는 게 안전

### A-2-3. 관계 유형 3가지 (178쪽)

| 유형 | 설명 | 블로그 예시 |
|---|---|---|
| 1:1 (일대일) | 한 레코드 ↔ 한 레코드 | 사용자 1명 = 프로필 1개 |
| 1:N (일대다) | 한 레코드 ↔ 여러 레코드 | 사용자 1명 = 게시글 여러 개 / 게시글 1개 = 댓글 여러 개 |
| N:N (다대다) | 여러 ↔ 여러 | 사용자가 여러 글에 좋아요 / 글이 여러 사용자에게 좋아요 받음 |

- 이 블로그 프로젝트는 **세 관계를 모두 사용**함
- SQL 문법 자체는 AI가 구현해주므로 책에서 다루지 않음 (단, 배워두면 유용)

> **체크포인트 A-2**
> 1. 우리 블로그에서 "좋아요"가 왜 N:N인지 설명해봐.
> 2. 외래키 제약을 안 걸면 어떤 이상한 데이터가 들어갈 수 있을까?

## A-3. 수파베이스란? (178~180쪽)

- PostgreSQL을 쉽고 빠르게 쓰도록 **호스팅 + 편의 기능**을 제공하는 서비스
- 우리는 PostgreSQL을 직접 만지지 않고 수파베이스를 통해서 사용

### A-3-1. 클라이언트 접근 vs 서버 접근 (178~179쪽)
- 수파베이스는 서버·클라이언트 **양쪽에서 접근 가능**
- Next.js도 클라이언트/서버 **양쪽에서 로직 실행 가능**
  - 서버에서 실행 → 서버가 페이지를 완성해서 브라우저로 보냄
  - 클라이언트에서 실행 → 응답받은 뒤 추가로 데이터를 따로 불러옴
- 그럼 데이터 처리는 어디서? → **둘 다 가능**
  - 서버가 대체로 더 안전 → 서버 접근이 편리
  - 클라이언트 직접 접근은 우리 서버를 안 거쳐 **이중 트래픽 과금이 없음**
- 이 챕터에서는 **두 방식을 모두 실습**함

### A-3-2. RLS 정책 (179~180쪽)
- RLS(Row Level Security) = 클라이언트 접근 시 **누가 어느 범위까지** 조회/생성/수정/삭제해도 되는지 명시하는 규칙
- 클라이언트에서 수파베이스를 쓸 땐 **필수**
- RLS를 켜면 **기본값은 전체 차단**, 정책으로 허가한 것만 통과
- 서버 접근은 왜 안전한가: 전체 데이터를 조회해도 서버 로직에서 클라이언트에 줘도 되는 형태로 다듬어 반환
- 클라이언트 접근이 왜 위험한가: 1번 사용자가 2번 사용자의 민감 정보에 접근 가능 + 우리 서버를 안 거치니 통제 불가
- **RLS의 한계** (중요)
  - 사람이 직접 작성 → 허점이 있을 수 있음
  - 클라이언트 요청의 위·변조를 검증할 수 없음
  - "완전한 보안 아키텍처"가 아님, 여전히 서버보다 위험
- 🔧 **데이터 조회가 안 되는 버그가 나면 RLS 정책부터 확인할 것**

> **체크포인트 A-3**
> 1. RLS를 켰는데 데이터가 하나도 안 보인다. 왜?
> 2. RLS가 있어도 서버 접근보다 위험한 이유 2가지를 말해봐.

### B-4-2. 마이그레이션 · 시드 개념 (192쪽)
- **마이그레이션(Migration)** = 요구사항에 맞춰 DB 구조를 정의·변경하는 단계
- **시드(Seed)** = 구조 테스트용 더미 데이터 생성
- 순서: **마이그레이션 먼저 → 시드 나중** ("그릇도 없는데 밥부터 푸면 안 됨")
- 마이그레이션 파일이 1개든 여러 개든 무관 — 순서대로 하나씩 적용되므로 결과는 동일
- ⚠️ **`supabase db reset`은 프로덕션에서 절대 금지**
  - 로컬은 괜찮지만 프로덕션 데이터는 날아가면 끝
  - 데이터가 아직 없어도 금지 (수파베이스 내장 기능용 리소스가 삭제될 수 있음)
  - 복구법은 백업 회귀 or 프로젝트 삭제 후 재생성뿐
  - AI가 추천하면 → "프로덕션 DB에서 **데이터 유실 없이** 마이그레이션하는 방법"을 다시 요청
- ⚠️ **바이브 UP! — sql 파일은 왜 옮기면 안 되나요?**
  - 수파베이스가 정의한 폴더 구조(`supabase/migrations/`, `supabase/seed.sql`)를 명령어가 그대로 사용
  - 이름·위치를 바꾸면 명령어가 정상 동작하지 않음

### B-4-3. RLS 정책 직접 확인 (193쪽)
- `migrations` 폴더의 마이그레이션 파일을 열어서 확인
  ```sql
  alter table categories enable row level security;
  alter table posts enable row level security;

  create policy "Public categories are viewable by everyone." on categories
    for select using (true);
  create policy "Public posts are viewable by everyone." on posts
    for select using (true);
  ```
- 지금은 **조회(select) RLS만** 있으면 충분 (홈페이지는 조회 기능뿐)
- 내 파일이 책과 완전히 같을 필요 없음
- 💡 확인 요령: `ROW LEVEL SECURITY`, `POLICY` 키워드를 **검색**해볼 것
- 아예 없으면 → "조회 RLS 정책을 생성해줘" 프롬프팅

### B-4-4. 수파베이스 CLI 연결 & 마이그레이션 적용 (194~195쪽)


3. 이유: 요청을 서버에서 했으므로 클라이언트는 그 요청의 존재조차 알 수 없음

   - 클라이언트와 서버는 전혀 다른 환경이고 제공 API도 다름
   - 그냥 지우면 다른 코드가 전부 깨질 가능성이 높음 → **반드시 AI를 통해 전환**
5. **클라이언트 사이드 렌더링은 절대 쓰면 안 되나요?**
   - 차이를 잘 알면 자유롭게 써도 됨. CSR은 다이나믹한 콘텐츠를 생동감 있게 보여주는 장점
   - 비개발자라면 **서버에서 DB 연동하는 게 비교적 안전**
   - 서버 렌더링이 많을수록 **SEO 유리 + TTFB 빠름**
   - TTFB(Time To First Byte) = 주소 입력 순간부터 브라우저가 첫 데이터를 받기까지의 시간. 초기 응답 속도 핵심 지표
   - 결론: 개발 지식이 없고 특별한 이유가 없다면 **최대한 서버에서**

# 부록. 이 챕터의 "진짜 학습 포인트" 8가지

빠짐없이 습득했는지 최종 자가 점검용.

1. CRUD ↔ HTTP 메서드 ↔ 엔드포인트 3단 대응을 자유롭게 왕복할 수 있다.
2. 상태 코드를 보고 프런트에서 무엇을 해야 하는지 판단할 수 있다.
3. 외래키·제약이 왜 "DB 수준"에서 강제되어야 하는지 설명할 수 있다.
4. RLS의 동작(기본 차단 + 허가) **과 한계**를 둘 다 말할 수 있다.
5. 마이그레이션과 시드를 구분하고, `db push`/`db reset`의 위험도 차이를 안다.
6. 에러 메시지에서 키워드(`row-level security policy`)를 뽑아 원인을 특정할 수 있다.
7. `'use client'` 하나로 데이터가 어디서 흐르는지 바뀐다는 걸 **Network 탭으로 증명**할 수 있다.
8. AI에게 문제를 넘길 때 "시도한 것 / 해결된 것 / 남은 문제" 형식으로 전달할 수 있다.
